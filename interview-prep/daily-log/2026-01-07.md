# Daily Interview Prep — January 07, 2026

Five questions worked through this session.

---

### Q1. Process vs thread?

**Answer.** A process is an isolated execution with its own address space and file handles; a thread is a unit of execution inside a process sharing that address space. Threads are cheap to create and communicate via shared memory (at the cost of synchronization); processes are isolated by default and talk via IPC.

---

### Q2. What is virtual memory?

**Answer.** Each process sees a private address space backed by the MMU, which maps virtual pages to physical frames via page tables. It gives isolation, overcommit (map more than RAM), lazy allocation, and the foundation for demand paging and copy-on-write fork.

---

### Q3. TCP vs UDP?

**Answer.** TCP: connection-oriented, reliable, in-order delivery with retransmission, flow and congestion control — for HTTP, databases. UDP: connectionless, no ordering or retransmit, tiny header — for video, DNS, game state, where a late packet is worse than a lost one. QUIC layers reliable streams over UDP.

---

### Q4. What happens when you type a URL and press enter?

**Answer.** DNS resolution (cache -> resolver -> root/TLD/authoritative servers), TCP handshake with the server, then the TLS handshake (certificate validation, key exchange), then the HTTP request/response. The browser parses HTML, fetches sub-resources, and renders.

---

### Q5. What is a deadlock and what are its conditions?

**Answer.** Two or more threads each hold a resource the other needs, so none can proceed. Needs four conditions (Coffman): mutual exclusion, hold-and-wait, no preemption, circular wait. Break any one — common practice: impose a global lock ordering to kill circular wait, or use try-lock with timeout/backoff.

---

### Q6. What is a database connection pool and why is it needed?

**Answer.** Connections are expensive to create (TCP + auth + TLS, tens of ms); a pool keeps N warm connections for the app to borrow/return. Pool size must respect the DB's max_connections — a common outage: 200 app nodes x pool of 20 = 4000 connections vs DB limit 1000. PgBouncer proxies to share physical connections.

---

### Q7. What does idempotency mean and how do you make writes idempotent?

**Answer.** Repeating the operation has no additional effect. Techniques: client-generated idempotency keys deduplicated server-side, PUT (replace, not append) semantics, and unique constraints (re-insert hits the constraint instead of duplicating). Needed for retries over networks where 'did it land?' is unknowable.

---

### Q8. How would you design a short URL service (bit.ly)?

**Answer.** Hash the long URL (or use a monotonic counter / base62 of an auto-increment id) to a 7-char code — counter avoids hash collisions and is cache-friendly. Store code->URL in a KV store or sharded DB, 301 redirect (caches the mapping in browsers) or 302 if you need click analytics. Handle load with a CDN + hot-key replication.

---

### Q9. What is a write-ahead log (WAL) and why is it important?

**Answer.** Every change is appended to a durable log before being applied to the data structures; crash recovery replays the log (redo) and rolls back uncommitted work (undo). It's what makes a database durable after a power loss, and the same log powers replication, point-in-time recovery, and compaction in LSM stores.
