# Daily Interview Prep — January 18, 2026

Five questions worked through this session.

---

### Q1. Why does a hash table give O(1) average lookup?

**Answer.** The key is passed through a hash function to index the bucket directly, skipping the scan. It degrades to O(n) when collisions cluster (poor hash or load factor too high), so implementations resize at ~0.7 load and use chaining or open addressing.

---

### Q2. What is a binary search tree and when does it degrade?

**Answer.** A BST keeps left < node < right, giving O(log n) search/insert on average. It degrades to O(n) when the tree becomes a chain (sorted insertions), which is why balanced variants (AVL, red-black) exist.

---

### Q3. Explain a min-heap and its typical use.

**Answer.** A complete binary tree stored in an array where each parent <= its children, so the root is always the minimum. Insert/sift is O(log n); it powers priority queues, top-k problems, Dijkstra, and merge-k-sorted-lists.

---

### Q4. How does an LRU cache work?

**Answer.** A hash map from key to node plus a doubly linked list for recency. On hit, move the node to the front; on insert, evict the back. Both operations are O(1).

---

### Q5. What is a trie and when would you use one?

**Answer.** A prefix tree where the path from root spells the key. Lookup/cost is O(key length), independent of dataset size. Used for autocomplete, spell-check, IP routing, and deduplicating prefix collisions in hash tables.

---

### Q6. What does ACID stand for and which level do NoSQL systems relax?

**Answer.** Atomicity (all-or-nothing transactions), Consistency (state transitions preserve invariants), Isolation (concurrent transactions don't interfere), Durability (committed data survives crashes). NoSQL systems like Cassandra sacrifice strong consistency/isolation (offer tunable levels, e.g. QUORUM) for availability and horizontal scale.

---

### Q7. Explain SQL isolation levels.

**Answer.** Read Uncommitted (dirty reads) < Read Committed (no dirty reads; non-repeatable reads possible) < Repeatable Read (same transaction sees the same data; phantom reads possible; InnoDB's default, mostly solved by gap locks) < Serializable (full serializability, via locking or SSI). Each step trades concurrency for correctness.

---

### Q8. What is MVCC and why do modern databases use it?

**Answer.** Multiversion concurrency control: writes create new row versions instead of overwriting; readers see a snapshot consistent with their transaction start. Readers never block writers and vice versa. Cost: version storage until a vacuum/garbage collector removes versions no snapshot needs (e.g. PostgreSQL autovacuum).
