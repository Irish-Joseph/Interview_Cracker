# Daily Interview Prep — January 28, 2026

Five questions worked through this session.

---

### Q1. How does a CDN work?

**Answer.** An edge network of caches geographically near users, addressed via DNS (CNAME to the CDN, then anycast/nearest-edge selection). Cacheable assets (HTML, JS, media) are served from the edge with cache-control keys; the origin only sees cache misses, cuts latency, and absorbs traffic spikes.

---

### Q2. What is rate limiting and name three strategies?

**Answer.** Bounded request acceptance per client/window. Token bucket (smooth bursts up to the bucket size), leaky bucket (constant outflow, smooths bursts), fixed/sliding window counters (simple, counter at window boundaries). Distributed deployments put the counters in Redis with atomic scripts or use an API gateway.

---

### Q3. What is a message queue and when would you use Kafka vs RabbitMQ?

**Answer.** A broker that decouples producers from consumers via durable, asynchronous messages. Kafka is a replicated, partitioned log — high throughput, replayable, event-sourcing/audit trails. RabbitMQ is a flexible work-queue router — lower latency per message, rich routing, but not a replay log.

---

### Q4. Microservices vs monolith?

**Answer.** Monolith: one deployable, shared database, simple transactions and debugging, coupled releases. Microservices: independent deploy/scale per service, polyglot persistence, isolated failure domains — at the cost of network latency, distributed-transaction complexity (sagas), and operational burden (tracing, versioning contracts).

---

### Q5. What is a B-tree and why do databases use it for indexes?

**Answer.** A multi-way balanced tree where each node holds many keys and child pointers, tuned so one node = one disk page. Height ~3-4 holds hundreds of millions of keys, so a point lookup is 3-4 page reads. Range scans are sequential page walks — better locality than a B+tree's leaf linked list... (B+trees are the usual choice; B-trees store data in all nodes).

---

### Q6. Explain SQL isolation levels.

**Answer.** Read Uncommitted (dirty reads) < Read Committed (no dirty reads; non-repeatable reads possible) < Repeatable Read (same transaction sees the same data; phantom reads possible; InnoDB's default, mostly solved by gap locks) < Serializable (full serializability, via locking or SSI). Each step trades concurrency for correctness.

---

### Q7. What is MVCC and why do modern databases use it?

**Answer.** Multiversion concurrency control: writes create new row versions instead of overwriting; readers see a snapshot consistent with their transaction start. Readers never block writers and vice versa. Cost: version storage until a vacuum/garbage collector removes versions no snapshot needs (e.g. PostgreSQL autovacuum).

---

### Q8. What's the difference between INNER, LEFT, RIGHT and FULL JOIN?

**Answer.** INNER: rows matching in both tables. LEFT: all left rows, NULLs where no match. RIGHT: mirror of LEFT. FULL: all rows from both, NULLs on either side for non-matches. LEFT JOIN with a WHERE on the right table's non-null column silently becomes an INNER JOIN — a classic bug.

---

### Q9. What is normalization and when would you denormalize?

**Answer.** Normalization (1NF..3NF, BCNF) removes redundancy and update anomalies by decomposing relations and keying facts. Denormalize when read latency matters more than write consistency — e.g. embedding an author's name in a posts table or a materialized aggregation — accepting that some write path must keep them in sync.

---

### Q10. What is an index, and why aren't more indexes always better?

**Answer.** A B+tree (typically) mapping key columns to row pointers, turning O(n) scans into O(log n) lookups. Composite indexes follow the leftmost-prefix rule. Costs: every index is written on INSERT/UPDATE/DELETE (write amplification, extra disk), and the planner can pick a bad index. Index for your actual queries, measured via EXPLAIN.
