# Daily Interview Prep — February 01, 2026

Five questions worked through this session.

---

### Q1. What is an ORM and what are its classic performance problems?

**Answer.** A library mapping objects to tables (SQLAlchemy, Hibernate). Classic problems: the N+1 query (looping entities and loading each relation lazily — fix with eager join/IN batch), over-fetching with big eager graphs, writing the whole object back (lost updates on concurrent writes), and hiding the SQL you actually shipped.

---

### Q2. What is a foreign key and does it always need an index?

**Answer.** A constraint declaring that a column's values must exist in the parent table's key, with cascade options (RESTRICT/NO ACTION, CASCADE, SET NULL). Most DBs automatically index FK columns (PostgreSQL does; MySQL InnoDB does) because the check needs it — don't assume, check the catalog.

---

### Q3. Explain primary key choices: UUID vs auto-increment vs surrogate?

**Answer.** Auto-increment (BIGINT): tiny, fast, cluster-friendly on InnoDB, but predictable (scrapers) and hard to merge shards. UUIDv4: random, no central authority, but 16 bytes scatter B-tree pages (write amplification) — UUIDv7 (time-ordered) fixes locality. Surrogate keys decouple business identity from storage identity.

---

### Q4. What is transactional outbox and why use it?

**Answer.** To keep 'update DB + publish event' atomic: write the event into an outbox table in the same local transaction as the data change, then a relay (polling or CDC like Debezium) publishes it to the broker. Consumers deduplicate (at-least-once delivery) — this is the standard way to avoid 2PC across services.

---

### Q5. What is the STAR method and why do interviewers prefer it?

**Answer.** Situation, Task, Action, Result — a structured story where the interviewer can see context, your specific contribution (Action is where 'I', not 'we', belongs), and a measurable outcome. It forces concrete evidence over generic claims, which is what behavioral screens actually score.

---

### Q6. What is a trie and when would you use one?

**Answer.** A prefix tree where the path from root spells the key. Lookup/cost is O(key length), independent of dataset size. Used for autocomplete, spell-check, IP routing, and deduplicating prefix collisions in hash tables.

---

### Q7. What does union-find (disjoint set) do?

**Answer.** It maintains groups of elements with union() and find(). Path compression + union by rank make each operation ~O(alpha(n)), effectively constant. Classic use: detecting connected components and cycles in undirected graphs.

---

### Q8. BFS vs DFS — when do you pick each?

**Answer.** BFS (queue) finds shortest unweighted paths and is level-order; DFS (stack/recursion) explores deep paths, suits topological sort, cycle detection in directed graphs, and tree traversal. DFS can also blow the stack on deep graphs — use an explicit stack if depth is unbounded.

---

### Q9. What is a skip list and why do databases use it?

**Answer.** A sorted linked list with extra 'express lanes' at higher levels, giving O(log n) expected search with much simpler, lock-friendly code than a balanced tree. LevelDB/RocksDB use it for their memtable because range scans are easy and concurrent insertion is cheap.

---

### Q10. What is a doubly linked list and what is its tradeoff?

**Answer.** Each node holds next and prev pointers, enabling O(1) removal if you have the node, and forward/backward iteration. Cost: 16 extra bytes per node and more pointer writes on mutation.
