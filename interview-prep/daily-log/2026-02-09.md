# Daily Interview Prep — February 09, 2026

Five questions worked through this session.

---

### Q1. How do you find the kth largest element faster than sorting?

**Answer.** Quickselect: partition like quicksort but recurse only into the side containing the kth element — average O(n), worst O(n^2) (fix with median-of-medians pivot or randomization). Or a size-k min-heap: O(n log k), which wins when k << n.

---

### Q2. What is the difference between BFS and Dijkstra on unweighted graphs?

**Answer.** On unweighted graphs Dijkstra degenerates to BFS — every relaxation has the same unit cost, so the heap never reorders anything. BFS is the simpler, faster choice there; keep Dijkstra for weighted edges.

---

### Q3. When would you use BFS on an adjacency list vs matrix?

**Answer.** Adjacency list: O(V + E) memory, ideal for sparse graphs (the common case). Matrix: O(V^2) memory but O(1) edge-existence checks and easy to combine with matrix operations — fine for dense graphs or small V with repeated queries.

---

### Q4. Process vs thread?

**Answer.** A process is an isolated execution with its own address space and file handles; a thread is a unit of execution inside a process sharing that address space. Threads are cheap to create and communicate via shared memory (at the cost of synchronization); processes are isolated by default and talk via IPC.

---

### Q5. What is virtual memory?

**Answer.** Each process sees a private address space backed by the MMU, which maps virtual pages to physical frames via page tables. It gives isolation, overcommit (map more than RAM), lazy allocation, and the foundation for demand paging and copy-on-write fork.

---

### Q6. How would you design a short URL service (bit.ly)?

**Answer.** Hash the long URL (or use a monotonic counter / base62 of an auto-increment id) to a 7-char code — counter avoids hash collisions and is cache-friendly. Store code->URL in a KV store or sharded DB, 301 redirect (caches the mapping in browsers) or 302 if you need click analytics. Handle load with a CDN + hot-key replication.

---

### Q7. What is a write-ahead log (WAL) and why is it important?

**Answer.** Every change is appended to a durable log before being applied to the data structures; crash recovery replays the log (redo) and rolls back uncommitted work (undo). It's what makes a database durable after a power loss, and the same log powers replication, point-in-time recovery, and compaction in LSM stores.

---

### Q8. What does ACID stand for and which level do NoSQL systems relax?

**Answer.** Atomicity (all-or-nothing transactions), Consistency (state transitions preserve invariants), Isolation (concurrent transactions don't interfere), Durability (committed data survives crashes). NoSQL systems like Cassandra sacrifice strong consistency/isolation (offer tunable levels, e.g. QUORUM) for availability and horizontal scale.

---

### Q9. Explain SQL isolation levels.

**Answer.** Read Uncommitted (dirty reads) < Read Committed (no dirty reads; non-repeatable reads possible) < Repeatable Read (same transaction sees the same data; phantom reads possible; InnoDB's default, mostly solved by gap locks) < Serializable (full serializability, via locking or SSI). Each step trades concurrency for correctness.

---

### Q10. What is MVCC and why do modern databases use it?

**Answer.** Multiversion concurrency control: writes create new row versions instead of overwriting; readers see a snapshot consistent with their transaction start. Readers never block writers and vice versa. Cost: version storage until a vacuum/garbage collector removes versions no snapshot needs (e.g. PostgreSQL autovacuum).

---

### Q11. What's the difference between INNER, LEFT, RIGHT and FULL JOIN?

**Answer.** INNER: rows matching in both tables. LEFT: all left rows, NULLs where no match. RIGHT: mirror of LEFT. FULL: all rows from both, NULLs on either side for non-matches. LEFT JOIN with a WHERE on the right table's non-null column silently becomes an INNER JOIN — a classic bug.

---

### Q12. What is normalization and when would you denormalize?

**Answer.** Normalization (1NF..3NF, BCNF) removes redundancy and update anomalies by decomposing relations and keying facts. Denormalize when read latency matters more than write consistency — e.g. embedding an author's name in a posts table or a materialized aggregation — accepting that some write path must keep them in sync.
