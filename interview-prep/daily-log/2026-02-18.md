# Daily Interview Prep — February 18, 2026

Five questions worked through this session.

---

### Q1. What is a foreign key and does it always need an index?

**Answer.** A constraint declaring that a column's values must exist in the parent table's key, with cascade options (RESTRICT/NO ACTION, CASCADE, SET NULL). Most DBs automatically index FK columns (PostgreSQL does; MySQL InnoDB does) because the check needs it — don't assume, check the catalog.

---

### Q2. Explain primary key choices: UUID vs auto-increment vs surrogate?

**Answer.** Auto-increment (BIGINT): tiny, fast, cluster-friendly on InnoDB, but predictable (scrapers) and hard to merge shards. UUIDv4: random, no central authority, but 16 bytes scatter B-tree pages (write amplification) — UUIDv7 (time-ordered) fixes locality. Surrogate keys decouple business identity from storage identity.

---

### Q3. What is transactional outbox and why use it?

**Answer.** To keep 'update DB + publish event' atomic: write the event into an outbox table in the same local transaction as the data change, then a relay (polling or CDC like Debezium) publishes it to the broker. Consumers deduplicate (at-least-once delivery) — this is the standard way to avoid 2PC across services.

---

### Q4. What is the STAR method and why do interviewers prefer it?

**Answer.** Situation, Task, Action, Result — a structured story where the interviewer can see context, your specific contribution (Action is where 'I', not 'we', belongs), and a measurable outcome. It forces concrete evidence over generic claims, which is what behavioral screens actually score.

---

### Q5. How do you answer 'Tell me about a time you disagreed with a teammate'?

**Answer.** Pick a real technical disagreement, show you steelmanned the other view, made the case with data/prototypes, and ended with a decision (yours or theirs) that you executed well. The signal is how you handle being wrong, not that you were right. Avoid 'I never disagree' — it reads as either conflict-avoidant or unengaged.

---

### Q6. How does a load balancer work and what are the common algorithms?

**Answer.** It front-ends a pool of servers and routes each connection using round-robin, least-connections, or consistent hashing (minimizes cache invalidation when nodes change). L4 operates on IP/TCP; L7 inspects HTTP (path, headers) and can add TLS termination, retries, and rate limiting.

---

### Q7. Horizontal vs vertical scaling?

**Answer.** Vertical: bigger machine — simple but capped by hardware and a single point of failure. Horizontal: more machines — requires statelessness or sharded/replicated state, load balancing, and network-aware code, but scales past any single box and allows rolling deploys.

---

### Q8. What is sharding and how do you choose a shard key?

**Answer.** Partition data across databases by a key: hash sharding spreads evenly (but range queries hit all shards), range sharding keeps locality (but risks hot ranges). Choose the key from your query patterns — a hot key (e.g. one user's 1B feed) skews load, so you may double-key (user_id, post_id).

---

### Q9. Explain database replication and the consistency tradeoff.

**Answer.** A primary writes, followers apply via the write-ahead log (async: fast, can lose commits on failover; semi-sync: at least one follower acks; sync: safest, slowest). Reads can go to followers for scale but may return stale data — mitigate with read-your-writes, session tokens, or fencing.

---

### Q10. What is consistent hashing and why do databases/CDNs use it?

**Answer.** Place nodes and keys on a ring (hash space); a key maps to the next node clockwise. Adding/removing a node moves only ~1/n of keys instead of reshuffling everything. Virtual nodes (replicas of a physical node on the ring) even out load and latency.

---

### Q11. How does a CDN work?

**Answer.** An edge network of caches geographically near users, addressed via DNS (CNAME to the CDN, then anycast/nearest-edge selection). Cacheable assets (HTML, JS, media) are served from the edge with cache-control keys; the origin only sees cache misses, cuts latency, and absorbs traffic spikes.

---

### Q12. What is rate limiting and name three strategies?

**Answer.** Bounded request acceptance per client/window. Token bucket (smooth bursts up to the bucket size), leaky bucket (constant outflow, smooths bursts), fixed/sliding window counters (simple, counter at window boundaries). Distributed deployments put the counters in Redis with atomic scripts or use an API gateway.

---

### Q13. What is a message queue and when would you use Kafka vs RabbitMQ?

**Answer.** A broker that decouples producers from consumers via durable, asynchronous messages. Kafka is a replicated, partitioned log — high throughput, replayable, event-sourcing/audit trails. RabbitMQ is a flexible work-queue router — lower latency per message, rich routing, but not a replay log.

---

### Q14. Microservices vs monolith?

**Answer.** Monolith: one deployable, shared database, simple transactions and debugging, coupled releases. Microservices: independent deploy/scale per service, polyglot persistence, isolated failure domains — at the cost of network latency, distributed-transaction complexity (sagas), and operational burden (tracing, versioning contracts).

---

### Q15. What is a B-tree and why do databases use it for indexes?

**Answer.** A multi-way balanced tree where each node holds many keys and child pointers, tuned so one node = one disk page. Height ~3-4 holds hundreds of millions of keys, so a point lookup is 3-4 page reads. Range scans are sequential page walks — better locality than a B+tree's leaf linked list... (B+trees are the usual choice; B-trees store data in all nodes).

---

### Q16. What is a database connection pool and why is it needed?

**Answer.** Connections are expensive to create (TCP + auth + TLS, tens of ms); a pool keeps N warm connections for the app to borrow/return. Pool size must respect the DB's max_connections — a common outage: 200 app nodes x pool of 20 = 4000 connections vs DB limit 1000. PgBouncer proxies to share physical connections.

---

### Q17. What does idempotency mean and how do you make writes idempotent?

**Answer.** Repeating the operation has no additional effect. Techniques: client-generated idempotency keys deduplicated server-side, PUT (replace, not append) semantics, and unique constraints (re-insert hits the constraint instead of duplicating). Needed for retries over networks where 'did it land?' is unknowable.
