# Daily Interview Prep — February 19, 2026

Five questions worked through this session.

---

### Q1. How would you estimate a project nobody has built before?

**Answer.** Decompose into known sub-parts, size each (story points or days) with explicit unknowns called out, identify the riskiest item first (spike/prototype it), and present a range with confidence, not a point number. Then name the milestones that would let you re-estimate mid-project.

---

### Q2. Walk through your biggest production bug.

**Answer.** Structure: what it was, how you detected it (monitoring vs user report — be honest), your diagnosis path, the fix, and the systemic change you made so it can't recur (alert, test, runbook, migration guard). The last part is what senior interviewers are actually grading.

---

### Q3. Why do you want to work here / on this team?

**Answer.** Reference something specific you researched: their architecture posts, an open-source project, a product decision you respect, or a stated engineering value. Generic answers ('great company, good culture') signal you sent 50 applications. Match your stated goals to what the team actually needs.

---

### Q4. How do you handle being stuck on a coding problem for 30 minutes?

**Answer.** Say what you've tried and what specifically is blocking, then ask for a nudge (interviewers expect this — silent spinning loses the round). If unsupervised: re-derive from a smaller case, brute-force first then optimize, and always communicate the partial solution and its complexity.

---

### Q5. What does code review actually check for, from a reviewer's view?

**Answer.** Correctness (does it do the spec?), clarity (naming, structure, dead code), tests (are the important paths covered?), and risk (failure modes, rollback, migration safety). As a reviewer, you're also judging the diff's size — a 3000-line PR is itself a process smell worth flagging.

---

### Q6. What does ACID stand for and which level do NoSQL systems relax?

**Answer.** Atomicity (all-or-nothing transactions), Consistency (state transitions preserve invariants), Isolation (concurrent transactions don't interfere), Durability (committed data survives crashes). NoSQL systems like Cassandra sacrifice strong consistency/isolation (offer tunable levels, e.g. QUORUM) for availability and horizontal scale.

---

### Q7. Explain SQL isolation levels.

**Answer.** Read Uncommitted (dirty reads) < Read Committed (no dirty reads; non-repeatable reads possible) < Repeatable Read (same transaction sees the same data; phantom reads possible; InnoDB's default, mostly solved by gap locks) < Serializable (full serializability, via locking or SSI). Each step trades concurrency for correctness.

---

### Q8. What is MVCC and why do modern databases use it?

**Answer.** Multiversion concurrency control: writes create new row versions instead of overwriting; readers see a snapshot consistent with their transaction start. Readers never block writers and vice versa. Cost: version storage until a vacuum/garbage collector removes versions no snapshot needs (e.g. PostgreSQL autovacuum).

---

### Q9. What's the difference between INNER, LEFT, RIGHT and FULL JOIN?

**Answer.** INNER: rows matching in both tables. LEFT: all left rows, NULLs where no match. RIGHT: mirror of LEFT. FULL: all rows from both, NULLs on either side for non-matches. LEFT JOIN with a WHERE on the right table's non-null column silently becomes an INNER JOIN — a classic bug.

---

### Q10. What is normalization and when would you denormalize?

**Answer.** Normalization (1NF..3NF, BCNF) removes redundancy and update anomalies by decomposing relations and keying facts. Denormalize when read latency matters more than write consistency — e.g. embedding an author's name in a posts table or a materialized aggregation — accepting that some write path must keep them in sync.

---

### Q11. What is an index, and why aren't more indexes always better?

**Answer.** A B+tree (typically) mapping key columns to row pointers, turning O(n) scans into O(log n) lookups. Composite indexes follow the leftmost-prefix rule. Costs: every index is written on INSERT/UPDATE/DELETE (write amplification, extra disk), and the planner can pick a bad index. Index for your actual queries, measured via EXPLAIN.

---

### Q12. What is a covering index?

**Answer.** An index that contains all columns the query needs (e.g. INCLUDE in PostgreSQL, or a composite wide enough), so the query is answered from the index alone — no heap 'bookmark lookups'. Common in OLTP for 'index-only scans' on hot read paths.

---

### Q13. Explain a B+tree index.

**Answer.** All data (or row pointers) lives in the leaf level, leaves are linked for range scans, and interior nodes are pure routing keys. Balanced and shallow (3-4 levels for hundreds of millions of rows). The leaf linked list makes sequential range reads a scan of adjacent pages — great for locality.

---

### Q14. What is a deadlock in a database and how do DBs handle it?

**Answer.** Two transactions each lock rows the other needs (T1 locks A waits for B; T2 locks B waits for A). MySQL InnoDB detects via a wait-for graph and kills the victim (ER_LOCK_DEADLOCK); PostgreSQL waits up to deadlock_timeout then detects and aborts one transaction. App fix: consistent lock ordering, short transactions, retry with backoff.
