# Daily Interview Prep — March 09, 2026

Five questions worked through this session.

---

### Q1. How do you prioritize when everything is urgent?

**Answer.** Impact x urgency vs effort, but first verify the urgency is real (a 'production is down' that's actually a 2% error rate is different). Make the tradeoff explicit to stakeholders rather than silently absorbing it, and leave room for the actual fire when it lands. Then describe how you communicate the deferral.

---

### Q2. What is the difference between a stack and a queue?

**Answer.** A stack is LIFO — push/pop both happen at the same end; a queue is FIFO — enqueue at the back, dequeue from the front. Stacks model undo, call frames, backtracking; queues model task scheduling, BFS, rate limiting.

---

### Q3. Why does a hash table give O(1) average lookup?

**Answer.** The key is passed through a hash function to index the bucket directly, skipping the scan. It degrades to O(n) when collisions cluster (poor hash or load factor too high), so implementations resize at ~0.7 load and use chaining or open addressing.

---

### Q4. What is a binary search tree and when does it degrade?

**Answer.** A BST keeps left < node < right, giving O(log n) search/insert on average. It degrades to O(n) when the tree becomes a chain (sorted insertions), which is why balanced variants (AVL, red-black) exist.

---

### Q5. Explain a min-heap and its typical use.

**Answer.** A complete binary tree stored in an array where each parent <= its children, so the root is always the minimum. Insert/sift is O(log n); it powers priority queues, top-k problems, Dijkstra, and merge-k-sorted-lists.

---

### Q6. What is rate limiting and name three strategies?

**Answer.** Bounded request acceptance per client/window. Token bucket (smooth bursts up to the bucket size), leaky bucket (constant outflow, smooths bursts), fixed/sliding window counters (simple, counter at window boundaries). Distributed deployments put the counters in Redis with atomic scripts or use an API gateway.

---

### Q7. What is a message queue and when would you use Kafka vs RabbitMQ?

**Answer.** A broker that decouples producers from consumers via durable, asynchronous messages. Kafka is a replicated, partitioned log — high throughput, replayable, event-sourcing/audit trails. RabbitMQ is a flexible work-queue router — lower latency per message, rich routing, but not a replay log.

---

### Q8. Microservices vs monolith?

**Answer.** Monolith: one deployable, shared database, simple transactions and debugging, coupled releases. Microservices: independent deploy/scale per service, polyglot persistence, isolated failure domains — at the cost of network latency, distributed-transaction complexity (sagas), and operational burden (tracing, versioning contracts).

---

### Q9. What is a B-tree and why do databases use it for indexes?

**Answer.** A multi-way balanced tree where each node holds many keys and child pointers, tuned so one node = one disk page. Height ~3-4 holds hundreds of millions of keys, so a point lookup is 3-4 page reads. Range scans are sequential page walks — better locality than a B+tree's leaf linked list... (B+trees are the usual choice; B-trees store data in all nodes).

---

### Q10. What is a database connection pool and why is it needed?

**Answer.** Connections are expensive to create (TCP + auth + TLS, tens of ms); a pool keeps N warm connections for the app to borrow/return. Pool size must respect the DB's max_connections — a common outage: 200 app nodes x pool of 20 = 4000 connections vs DB limit 1000. PgBouncer proxies to share physical connections.

---

### Q11. What does idempotency mean and how do you make writes idempotent?

**Answer.** Repeating the operation has no additional effect. Techniques: client-generated idempotency keys deduplicated server-side, PUT (replace, not append) semantics, and unique constraints (re-insert hits the constraint instead of duplicating). Needed for retries over networks where 'did it land?' is unknowable.

---

### Q12. How would you design a short URL service (bit.ly)?

**Answer.** Hash the long URL (or use a monotonic counter / base62 of an auto-increment id) to a 7-char code — counter avoids hash collisions and is cache-friendly. Store code->URL in a KV store or sharded DB, 301 redirect (caches the mapping in browsers) or 302 if you need click analytics. Handle load with a CDN + hot-key replication.
