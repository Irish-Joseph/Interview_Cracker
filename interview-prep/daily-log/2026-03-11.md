# Daily Interview Prep — March 11, 2026

Five questions worked through this session.

---

### Q1. What is a doubly linked list and what is its tradeoff?

**Answer.** Each node holds next and prev pointers, enabling O(1) removal if you have the node, and forward/backward iteration. Cost: 16 extra bytes per node and more pointer writes on mutation.

---

### Q2. How do balanced BSTs (AVL / red-black) stay balanced?

**Answer.** AVL enforces height difference <= 1 via rotations after inserts/deletes — tighter, better for search. Red-black allows larger imbalance but uses at most 2 rotations per insert, so it's favored when insert/delete dominate (e.g., Java TreeMap, Linux CFS).

---

### Q3. What is a sliding window and what does it solve?

**Answer.** Maintain [left, right) over an array with O(1) amortized adds/removes from the ends. Solves fixed-size window max/sum, and variable-size problems like 'longest substring without repeating chars' by shrinking when the constraint breaks.

---

### Q4. Explain quicksort and its worst case.

**Answer.** Pick a pivot, partition around it, recurse. Average O(n log n), in-place, cache-friendly. Worst case O(n^2) on sorted input with naive first/last pivot — fixed by randomized or median-of-three pivot. It's not stable.

---

### Q5. Why is merge sort O(n log n) always, and what does it cost?

**Answer.** It splits in half (log n levels) and each level merges in O(n). Guarantees n log n regardless of input and is stable, but needs O(n) auxiliary space — that's the cost.

---

### Q6. What is an index, and why aren't more indexes always better?

**Answer.** A B+tree (typically) mapping key columns to row pointers, turning O(n) scans into O(log n) lookups. Composite indexes follow the leftmost-prefix rule. Costs: every index is written on INSERT/UPDATE/DELETE (write amplification, extra disk), and the planner can pick a bad index. Index for your actual queries, measured via EXPLAIN.

---

### Q7. What is a covering index?

**Answer.** An index that contains all columns the query needs (e.g. INCLUDE in PostgreSQL, or a composite wide enough), so the query is answered from the index alone — no heap 'bookmark lookups'. Common in OLTP for 'index-only scans' on hot read paths.

---

### Q8. Explain a B+tree index.

**Answer.** All data (or row pointers) lives in the leaf level, leaves are linked for range scans, and interior nodes are pure routing keys. Balanced and shallow (3-4 levels for hundreds of millions of rows). The leaf linked list makes sequential range reads a scan of adjacent pages — great for locality.
