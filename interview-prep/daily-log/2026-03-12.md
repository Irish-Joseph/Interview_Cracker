# Daily Interview Prep — March 12, 2026

Five questions worked through this session.

---

### Q1. What is a count sort / radix sort and when is it valid?

**Answer.** Counting sort buckets by integer value in O(n + k) — linear when k is bounded, so it beats comparison sort's n log n floor. Radix sort generalizes it digit-by-digit. Only works on bounded integers (or fixed-length keys).

---

### Q2. What do we mean when we say an algorithm is O(n log n)?

**Answer.** Runtime grows proportionally to n log n: n log n = n x log n, n x log2 n = n x 10. Big-O hides constants and lower-order terms, so 10n log n is also O(n log n). It describes the asymptotic upper bound of the worst-case behavior we analyzed.

---

### Q3. Explain the two-pointer technique.

**Answer.** Keep left and right pointers moving inward (or both moving forward) to exploit monotonic structure — sorted arrays, prefix structure, window validity. Reduces brute-force O(n^2) to O(n) for problems like two-sum on sorted arrays, container-with-most-water, and palindrome checks.

---

### Q4. When is binary search the right tool, and what's the classic bug?

**Answer.** Use it on any monotonic predicate (sorted array, or 'find first true over a boolean space'), giving O(log n). Classic bugs: integer overflow in mid = (lo+hi)/2 (use lo + (hi-lo)/2), off-by-one on update bounds, and wrong loop invariant (use [lo, hi) or consistently <=).

---

### Q5. Describe Dijkstra's algorithm and its limitation.

**Answer.** Greedy shortest-path from one source using a min-heap: settle the closest unsettled node, relax edges. O((V+E) log V). Fails with negative edge weights because a settled node's distance can still decrease — use Bellman-Ford there.

---

### Q6. What is an ORM and what are its classic performance problems?

**Answer.** A library mapping objects to tables (SQLAlchemy, Hibernate). Classic problems: the N+1 query (looping entities and loading each relation lazily — fix with eager join/IN batch), over-fetching with big eager graphs, writing the whole object back (lost updates on concurrent writes), and hiding the SQL you actually shipped.

---

### Q7. What is a foreign key and does it always need an index?

**Answer.** A constraint declaring that a column's values must exist in the parent table's key, with cascade options (RESTRICT/NO ACTION, CASCADE, SET NULL). Most DBs automatically index FK columns (PostgreSQL does; MySQL InnoDB does) because the check needs it — don't assume, check the catalog.

---

### Q8. Explain primary key choices: UUID vs auto-increment vs surrogate?

**Answer.** Auto-increment (BIGINT): tiny, fast, cluster-friendly on InnoDB, but predictable (scrapers) and hard to merge shards. UUIDv4: random, no central authority, but 16 bytes scatter B-tree pages (write amplification) — UUIDv7 (time-ordered) fixes locality. Surrogate keys decouple business identity from storage identity.

---

### Q9. What is transactional outbox and why use it?

**Answer.** To keep 'update DB + publish event' atomic: write the event into an outbox table in the same local transaction as the data change, then a relay (polling or CDC like Debezium) publishes it to the broker. Consumers deduplicate (at-least-once delivery) — this is the standard way to avoid 2PC across services.

---

### Q10. What is the STAR method and why do interviewers prefer it?

**Answer.** Situation, Task, Action, Result — a structured story where the interviewer can see context, your specific contribution (Action is where 'I', not 'we', belongs), and a measurable outcome. It forces concrete evidence over generic claims, which is what behavioral screens actually score.

---

### Q11. How do you answer 'Tell me about a time you disagreed with a teammate'?

**Answer.** Pick a real technical disagreement, show you steelmanned the other view, made the case with data/prototypes, and ended with a decision (yours or theirs) that you executed well. The signal is how you handle being wrong, not that you were right. Avoid 'I never disagree' — it reads as either conflict-avoidant or unengaged.

---

### Q12. How would you estimate a project nobody has built before?

**Answer.** Decompose into known sub-parts, size each (story points or days) with explicit unknowns called out, identify the riskiest item first (spike/prototype it), and present a range with confidence, not a point number. Then name the milestones that would let you re-estimate mid-project.
