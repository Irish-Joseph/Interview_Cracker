# Daily Interview Prep — August 07, 2026

Focus: data structures. 2 questions worked through this session.

---

### Q1. What is a memory leak?

**Answer.** Memory that is no longer reachable through any pointer but was never freed (or is kept alive by an unintended reference). Symptoms: slow RSS growth, eventual OOM. Sources: unremoved listeners/cache entries, reference cycles (in refcounted runtimes without GC), leaked native handles.

---

### Q2. Explain reference counting vs tracing garbage collection.

**Answer.** Refcounting frees an object the moment its count hits zero — simple and immediate, but cannot collect cycles and the per-pointer overhead is real. Tracing GC (mark-and-sweep, generational, e.g. G1/ZGC) scans from roots, handles cycles, but introduces pauses or pauses-hiding (ZGC uses colored pointers for concurrent collection).

---

### Q3. What is an ORM and what are its classic performance problems?

**Answer.** A library mapping objects to tables (SQLAlchemy, Hibernate). Classic problems: the N+1 query (looping entities and loading each relation lazily — fix with eager join/IN batch), over-fetching with big eager graphs, writing the whole object back (lost updates on concurrent writes), and hiding the SQL you actually shipped.

---

### Q4. What is a foreign key and does it always need an index?

**Answer.** A constraint declaring that a column's values must exist in the parent table's key, with cascade options (RESTRICT/NO ACTION, CASCADE, SET NULL). Most DBs automatically index FK columns (PostgreSQL does; MySQL InnoDB does) because the check needs it — don't assume, check the catalog.

---

### Q5. Explain primary key choices: UUID vs auto-increment vs surrogate?

**Answer.** Auto-increment (BIGINT): tiny, fast, cluster-friendly on InnoDB, but predictable (scrapers) and hard to merge shards. UUIDv4: random, no central authority, but 16 bytes scatter B-tree pages (write amplification) — UUIDv7 (time-ordered) fixes locality. Surrogate keys decouple business identity from storage identity.
